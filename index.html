02

FIRST RUN

From files to a working interface.

Keep the four Python files and requirements.txt together in a local folder. Use Windows, Python 3.10 or later, Tkinter, and the pinned pywin32 dependency. Validate your Python version and target Windows environment before deployment.

1

Prepare the Python environment

Open PowerShell in the application folder. Install dependencies into the same interpreter used to run the app.

POWERSHELL
python -m pip install -r requirements.txt

For SYSTEM execution, that interpreter, its DLLs, pywin32 and the project files must also be accessible to LocalSystem.

2

Open the desktop interface

The main entry point opens the GUI with no arguments, or with --gui.

POWERSHELL
python .\run_in_session.py --gui
3

Choose, configure, simulate

Select Destination session, browse to an executable, add arguments if needed, and select Simulate. An actual launch requires the launcher to run as SYSTEM.

IMPORTANT DISTINCTION

Administrator is not SYSTEM. The normal launch engine uses the selected source account token for the target process. The separate SYSTEM launcher starts the Run in Session GUI itself as SYSTEM.

03

DESTINATION MATTERS

Make the session an explicit choice.

DESKTOP INTERFACE

One destination, two controls.

The Destination session dropdown and session table stay synchronized. Each entry shows the Windows ID, qualified account, connection state and station name.

  • Use F5 to refresh both views.
  • Use Ctrl + F to focus search.
  • Filtering out the selected destination clears it; another user is never silently selected.
  • Use Ctrl + Enter to simulate.
COMMAND LINE

Prefer an exact ID.

Use --session 3 for a known ID. Use --user 'DOMAIN\operator' for an account with exactly one matching session.

Multiple matches are rejected, including two sessions belonging to the same account. Select an explicit ID to continue.

Session data can change between checks and launch. Refresh after logon, logoff or an RDP reconnection.

ACCOUNT AND DESKTOP ARE INDEPENDENT

To run as an account from one session on another user's desktop, choose the destination in Destination session and the account in Run as account (source session). The default Same as destination preserves the usual behavior.

For a cross-session launch, start the SYSTEM GUI inside the destination session and explicitly enable Allow source logon to access destination desktop. This grants GUI access to that source logon SID only; it can remain until destination logoff, even after the launched process exits or creation fails. It does not grant Everyone access, DACL ownership, or hook/journal rights. Do not use a shared desktop for mutually untrusted accounts.

The source user must already be logged on. No password is requested. Simulation does not modify tokens or desktop permissions. Actual interactive launch remains an integration check in the destination environment.

SYSTEM INFORMER-STYLE TOKEN OPTIONS

Choose the token properties explicitly.

  • Toggle elevation requests the same account's linked primary UAC token. It toggles between limited and elevated when a valid split token exists; it does not turn a standard account into an administrator. If no valid linked token is available, the launch fails explicitly instead of silently keeping the original token.
  • Create UIAccess requests the UIAccess flag on the duplicated token through the Windows API. SYSTEM/SeTcbPrivilege and the VDI's policy must permit it. A denied request fails; no Windows policy is disabled or changed. Unchecked preserves the selected token's existing UIAccess state.
  • Create suspended leaves the verified process suspended. Resume or terminate that PID explicitly in your process-management tool. Do not combine it with waiting; closing the launcher does not resume it.

Every launch is initially suspended. The application reads the new process token, checks identity, destination session, elevation, UIAccess and integrity against the prepared token, then resumes it unless you requested suspended creation. A mismatch or inspection failure requests termination and reports whether termination was confirmed. If cleanup is unconfirmed, inspect the PID before retrying.

How does the launcher work?

It registers a uniquely named, on-demand scheduled task under LocalSystem, restricted to administrators and SYSTEM. The helper duplicates its own SYSTEM token, assigns the chosen session ID and requests process creation on winsta0\default.

The helper requests job breakaway so the GUI can outlive it. If Windows job policy rejects that request, the launch fails rather than silently trying a different method. A completed helper's task is deleted; an unknown result leaves the task available for diagnostics.

No recurring trigger or automatic privilege elevation is configured. Successful process creation does not confirm that Tkinter or the application finished loading. Real SYSTEM launch remains an environment-dependent integration check.

TWO DIFFERENT DESTINATIONS

The launcher's session choice controls where the SYSTEM GUI opens. Inside that GUI, Destination session controls where the target program runs. Run as account (source session) independently chooses its execution identity. These choices can be different.

A scheduled task running in session 0 alone does not make a GUI visible on a user's desktop. See Microsoft's interactive services documentation for the session boundary.

FEEDBACK YOU CAN INTERPRET

Created. Finished. Or no longer monitored.

What simulation checks

  • Input and session state.
  • A logged-on, readable user.
  • Working directory existence.
  • The explicit executable path in the current context.

What it does not prove

  • Sufficient launch or desktop permissions.
  • Executable access as the target user.
  • A ready user profile or application environment.
  • That the application will start successfully.

VDI VERIFICATION WORKFLOW

After launch, read the Verified PID log line or select Export token JSON. Compare that PID in System Informer: user/SID, session ID, Elevated, Elevation Type, UIAccess and integrity level. The report records the initial token and whether the initial thread was resumed or left suspended. It does not prove that a window appeared, that the application finished loading, or that later child processes kept the same token.

To inspect an existing PID without changing it, run the following command. Use it for both the process created by this application and the one created by System Informer. A PID can be reused after exit, so inspect the correct live process promptly. This read-only report has verified_against_request=false because it has no original launch request to compare.

READ-ONLY PID INSPECTION
python .\run_in_session.py --inspect-pid 1234

JSON exports include account and SID metadata. Store or share them intentionally; they contain no password or target arguments. Validation on the actual remote VDI remains required.

These codes describe run_in_session.py. The separate SYSTEM launcher reports helper failures separately. Without --wait, success confirms creation only. With --wait and no timeout, the CLI waits indefinitely.

07

RECOVER WITH CONTEXT

When something needs attention.

“No module named win32ts”

win32ts is part of pywin32. Install requirements.txt using the same Python interpreter that starts the application. A second Python installation or the SYSTEM account may resolve a different environment. See the pywin32 project documentation.

The session I need is missing

Refresh with F5, clear search and review the table. Only eligible user sessions appear in the destination dropdown. The user must be logged on and the account readable. A listener or session 0 is not an interactive target.

Toggle elevation or UIAccess was rejected

A standard account may have no linked UAC token. Toggle elevation then fails explicitly; uncheck it if you intend to keep the original token. UIAccess is a separate flag, not desktop ACL access or administrator membership. If Windows rejects it, review the reported error and the VDI policy rather than changing the operating system's security settings automatically.

Access denied or SeTcbPrivilege is unavailable

The main launch engine requires LocalSystem with SeTcbPrivilege. An elevated administrator shell is sufficient to request the SYSTEM scheduled-task helper, but does not itself become SYSTEM. Check local task policy and the printed error; do not treat a simulation as proof of permission.

A SYSTEM request has no confirmed result

Inspect the named RunInSession-Launch-… task in Windows Task Scheduler. Do not immediately repeat the request: a process may already have been created. Tasks without a confirmed result are retained for diagnostics and have no recurring trigger.

The process launched, but no window appeared

Check the selected session and whether it is disconnected. The program may be non-graphical, may exit during startup, or may lack access to its desktop, files or profile. Creation alone does not prove application readiness. The engine creates an environment block but does not explicitly load a user profile.

What happens when I close the GUI?

During an operation, closing can be deferred until the Windows call finishes. Waiting is interrupted, but an already created target is not terminated. A blocked Windows call can delay closing. The log distinguishes launch, exit, timeout and stopped monitoring.

Are arguments or session details uploaded?

The application is local. Target arguments are excluded from its activity log, but remain visible in the GUI and the Windows process command line. Actual account and session details are read locally at runtime. This static guide has no analytics or network API calls; theme preference is stored only in the browser.
